# 推测睡眠算法说明

实现位置：`algorithm` 模块，入口为 `SleepCalculator.compute(...)`。该模块不依赖 Android 框架。锁屏事件用与 `UsageEvents.Event` 相同的整型：`KEYGUARD_SHOWN = 17`，`KEYGUARD_HIDDEN = 18`（API 28+）。

时区固定为 `Asia/Shanghai`。`day_date` 是**夜间窗口开始的那个日历日**（当天 22:00 所属的日期），即使醒来已经是次日。

`sleep_start` / `sleep_end` 只使用真实事件边界（某次前台 `PAUSED`、`RESUMED`，或一次 `KEYGUARD_HIDDEN`），不把 22:00、10:00 或采集区间终点当成入睡 / 醒来。

## 前台会话

1. **排序事件**：按时间戳升序；同一毫秒时先处理 `PAUSED`，再处理 `RESUMED`。
2. **组装前台会话**
   - `RESUMED` 开始一段会话；同一包连续多次 `RESUMED`（Activity 内跳转）保留第一次开始时间。
   - `PAUSED` 关闭对应包的会话。
   - **未匹配的 PAUSED** 直接忽略。
   - **应用切换**：若 A 仍打开时出现 B 的 `RESUMED`，在 B 的开始时刻关闭 A。
   - **区间结束仍未关闭的 RESUMED**：结束时间填为 `rangeEnd`，`closed = false`。这个填充时间**不能**当作入睡点。
3. 间隔不超过 `MAX_BRIEF_INTERRUPTION_MS`（3 分钟）的相邻会话并成同一次「拿起手机」，避免把一次使用拆开。

## 入睡

入睡 = 一段合格长静默的**起点**，也就是上一次真实使用的结束时间（不裁剪到 22:00）。因此 20:00 放下手机、次日早上再打开，入睡时间记 20:00。

合格条件与原来相同：

- 静默时长 ≥ `MIN_SLEEP_GAP_MS`（默认 90 分钟）；
- 且与至少一个夜间窗口有正时长重叠。夜间窗口为当天 22:00 至次日 10:00。
- 不从 `rangeStart` 凭空造间隙。没有下一次真实边界时，开口间隙不是睡眠。

短暂中断（见下）不会把一夜切成两段，所以入睡仍落在**最初那段**长静默的起点，而不是闹钟之后剩下的那一段。若夜里有一次**超过 3 分钟**的真实使用把睡眠切开，同一夜间窗口仍只保留最长的一段。

一条长间隙若与两个夜间窗口都重叠，归给**重叠更长**的那个窗口；重叠时长相同则取更早的日期。同一间隙绝不会记成两天。

## 醒来

醒来 = 入睡之后第一次**真正起床**，不是锁屏上的任何前台活动。

1. **主信号是解锁。** 输入里只要出现过 `KEYGUARD_HIDDEN`，就用它作为醒来时间：
   - 应用打开前 3 分钟内的解锁，优先于紧随其后的 `RESUMED`；
   - 先在锁屏上响铃、再解锁时，取这段使用期间的**第一次** `KEYGUARD_HIDDEN`，而不是更早的闹钟 `RESUMED`。
2. **锁屏活动不算醒来。** 没有 `KEYGUARD_HIDDEN` 的短前台（不超过 3 分钟，例如关掉闹钟、看一眼时间）直接忽略，即使它后面马上就有真正的解锁。
3. **短暂中断。** 解锁之后，若这次使用不超过 3 分钟，**并且**解锁到下一次 `KEYGUARD_SHOWN` 也不超过 3 分钟，而且前后都还有一段 ≥ 90 分钟、与夜间窗口重叠的静默，则不结束睡眠。前后静默合并。睡眠仍从原来的入睡时间算起，醒来记到下一次真正解锁。超过 3 分钟的使用或解锁，这次解锁就是醒来。
4. **长时间使用但没有解锁事件。** 入睡之后若有一段超过 3 分钟的前台，而这段里没有 `KEYGUARD_HIDDEN`，用该段会话的**开始时间**作为醒来。用来覆盖个别夜晚漏记锁屏事件的机型。
5. **整段输入完全没有 `KEYGUARD_HIDDEN`。** 退回按前台会话估算醒来（下一次使用的开始），但夜间窗口里被两段长静默夹住、且不超过 3 分钟的会话仍视为中断并合并。这样旧数据或不记录解锁的机型不会被每一次亮屏切碎；若短会话后面没有再出现使用，它本身仍是醒来（不编造一个更晚的时间）。
6. **采集结束时仍解锁。** 最后一次 `KEYGUARD_HIDDEN` 之后没有 `KEYGUARD_SHOWN`，也没有更晚的使用边界，把这次解锁当作醒来。已经重新锁屏的短暂中断不是这种情形。

## raw_sessions

与该夜间窗口相交的前台会话，并至少包含入睡前最后一次会话。锁屏上被忽略的闹钟会话仍会出现在这里，供界面核对，但它不决定 `sleep_end`。

## 日志

采集时会把 `queryEvents` 总条数，以及 `RESUMED/PAUSED`、`KEYGUARD_SHOWN`、`KEYGUARD_HIDDEN` 的条数打到 `SleepCollect`。若某台小米手机的 `KEYGUARD_HIDDEN` 长期为 0，说明系统没记解锁，算法会走上面的前台回退。

计算完成后，每条静默间隙的起止、时长、是否通过过滤、过滤原因、是否被选为当日睡眠也会打到 `SleepCollect`。
